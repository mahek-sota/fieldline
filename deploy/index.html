I’m Mahek Sota, a software engineer at the University of Mississippi. Charge’s Hacker News post got me thinking about what happens once a mobile solar factory is running on a job site. If installation slows down, how does the crew tell whether a machine faulted, materials arrived late, or a station has been getting slower over several shifts? I built Fieldline to explore that question with five days of simulated site data.

Why Charge Robotics

  • Build solar faster. I was surprised that installation could hold back solar deployment, and I want to help tackle that bottleneck.
  • See software work in the field. I’d love to see a tool I built help a crew figure out why the line slowed down.
  • Build with operators. I want to learn what crews need during a shift and improve the tools based on their feedback.

What I’d bring to Charge

  • Reliable data pipelines. I’ve built Python, Kafka, and PostgreSQL pipelines that processed 50M+ records.
  • Tools for troubleshooting. Fieldline shows where time went and which station started slowing down.
  • End-to-end ownership. At Ole Miss, I work directly with users and own tools from scoping through deployment and support.

How I approached it

1One question

Where does the machine lose time? Every chart answers part of it.

2Simulate, and say so

Seeded model of four stations, random faults, late parts, one wearing station.

3Assume the network fails

Local outbox, batched upload, replay after an outage, server ignores repeats.

4Explainable analysis

CUSUM on cycle times, so every alarm traces back to numbers a technician can check.

5Keep it small

One weekend and three tests that matter.
